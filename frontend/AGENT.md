# MetaTwinWear 项目规范

## 1. 规范定位

本文件同时面向 AI Agent 和人工开发者，仅适用于 `frontend/` 目录及其下的新代码与后续维护工作。

规则按以下级别理解：

- **必须**：除非有明确且已记录的例外，否则不可违反。
- **应该**：默认遵守；确有合理原因时可以偏离。
- **可以**：允许采用，但不是强制要求。

项目当前技术栈：Vue 3、TypeScript、Vite、Pinia、Element Plus、ECharts、Tailwind CSS v4、SCSS。

## 2. Agent 工作方式

### 必须

- 修改前先阅读相关文件、现有实现和项目配置，确认当前约定后再行动。
- 采用最小范围修改，避免无关重构和行为变化。
- 涉及类型或构建行为的修改必须执行 `npm run build`。
- 代码保留必要的简要说明注释。
- 完成任务时报告实际修改内容。

### 应该

- 优先复用已有组件、类型、composable、store 和样式变量。
- 根据改动范围执行相关验证，不为纯文档修改额外引入工具或测试框架。
- 发现与当前任务无关的问题时只报告，不扩大任务范围。

## 3. Vue 与 TypeScript

### 必须

- 新增或重写 Vue 组件统一使用 Composition API 和 `<script setup lang="ts">`。
- 组件文件使用 PascalCase 命名，例如 `DashboardPanel.vue`。
- 代码标识符、类型名和公共 API 使用英文命名。
- 跨目录引用优先使用现有 `@/` 路径别名。
- 局部交互状态使用组件内的 `ref` 或 `reactive`；跨组件或跨页面共享状态使用 Pinia。
- Vue 模板中复杂或职责不直观的标签、区域应添加简短注释说明其功能职责；简单且语义明确的结构无需重复注释。

### 应该

- 优先使用明确的 TypeScript 类型，并让类型沿数据边界传递。
- `any` 仅用于第三方库兼容、遗留代码边界或暂时无法修复的外部类型问题；使用时应通过注释或代码上下文说明原因。
- 公共组件的 Props、Emits 和对外数据结构应该有清晰的类型定义。
- 注释应解释业务原因、约束或非显而易见的实现决策，避免重复描述代码本身。

## 4. 目录与模块组织

现有目录结构可以继续使用，不要求为了本规范立即迁移已有文件。

### 必须

- 新增功能优先按业务功能模块组织，而不是无条件增加全局技术层目录。
- 功能模块中的组件、composable、store、类型和 mock 数据应该保持就近组织。
- 与具体业务无关的通用能力放入 shared 类目录，避免被某个业务模块私有化后重复实现。

推荐的新功能组织形式：

```text
src/
  features/
    dashboard/
      components/
      composables/
      mock/
      stores/
      types/
  shared/
    components/
    composables/
    types/
```

该结构是新增代码的演进方向，不要求一次性改造当前的 `components`、`stores`、`types` 等目录。

## 5. 数据访问与状态

### 必须

- 组件不得直接调用 API，也不得直接读取 Mock 数据。
- 组件通过 composable 或 Pinia 获取业务数据、状态和动作。
- Mock 数据与真实 API 使用共享类型，保证数据源可以逐步替换。
- 数据模块应明确处理 loading、error、empty 和 success 状态；不能静默吞掉关键请求失败。

### HTTP API 响应约定

- `/api/v1/**` 的 JSON API 使用 `ApiResponse<T>` 统一结构：`code`、`message`、`success`、`data`；HTTP 状态码与 `code` 一致。`data` 才是业务对象，前端 API 边界应在成功时解包并向 Store、composable 和组件提供业务数据，不让页面依赖响应信封。
- 请求失败或响应 `success: false` 时优先使用后端 `message` 展示错误；不得把失败响应当作成功业务数据，也不得静默忽略解析错误。
- SSE 的 `snapshot`、`heartbeat` 事件数据同样是 `ApiResponse<T>`，解析后再更新状态；错误或无效事件应转换为可见的连接错误状态。
- 图片成功响应为原始 `image/jpeg`，通过图片 URL 加载，不按 JSON 响应解析；图片加载失败应显示适当的错误状态。
- 上述信封约定只适用于真实 API；Mock 数据继续使用共享的业务数据类型，不额外包一层 `ApiResponse`。

### 应该

- 将数据获取、转换、轮询和副作用放在 composable、store 或数据访问边界内，不放入纯展示组件。
- 页面和组件只依赖稳定的业务数据接口，不依赖 Mock 的内部结构。
- 对用户可见的错误提供可理解的状态或提示，对开发者保留足够的诊断信息。

## 6. ECharts 图表

### 必须

- 图表组件根据传入的业务数据和必要参数，在组件内部通过 `computed` 生成 ECharts option。
- 页面层不应为每个图表重复组装完整的 ECharts option。
- 图表配置应使用类型化的 ECharts 配置，避免通过无类型对象传递配置。

### 应该

- 图表组件负责图表视觉默认值、坐标轴、提示框和系列映射；页面只负责提供业务数据。
- 复杂或重复的 option 片段可以抽取为模块内的工厂函数或共享配置，但不要为了抽象而拆分简单配置。

## 7. UI、样式与视觉

### 必须

- 通用表单、按钮、选择器等交互优先复用 Element Plus。
- 项目特有视觉通过封装组件、主题样式或局部样式实现，不在多个页面复制相同的交互实现。
- 重复使用的颜色和设计令牌优先使用 CSS 变量。
- 样式可以使用 SCSS，也可以使用组件内的 scoped style。
- 交互元素必须可操作；图片应提供语义替代信息；颜色不能作为唯一的状态表达方式。

### 应该

- 设计稿还原优先于过度抽象，但固定尺寸和视觉魔法值应限制在确有设计依据的范围内。
- 优先保证桌面和大屏布局，同时兼顾平板宽度下的可用性。
- 以现代主流浏览器为支持目标，不为过旧浏览器增加未经要求的兼容层。
- 统一复用现有设计变量、面板、标题和图表等视觉基础组件。

### Tailwind CSS 与 SCSS 分工

- Dashboard 的页面骨架、导航排列、栏位顺序和主要图表网格优先使用 Tailwind 响应式工具类；`md` 对应 `768px`，`xl` 对应 `1280px`。
- Tailwind 通过 Vite 插件接入，只导入 theme 和 utilities，不启用 Preflight，避免重置 Element Plus 与现有基础样式。
- 颜色、面板装饰、图表细节和复杂交互样式沿用现有 CSS 变量与 SCSS；新增样式应复用已有设计变量。
- 同一元素的同一布局属性不得同时由 Tailwind 工具类和未分层的 SCSS 规则控制；迁移布局时同步移除旧规则及其断点覆盖。
- Tailwind 类名应以完整静态字符串写在 Vue 模板中，确保构建时能够扫描到响应式类。

### 字体与字号

- 页面主要文字、面板标题和核心指标默认使用 `16px`，作为项目的主字号。
- 普通内容、按钮、表单值和次级指标使用 `14px`；辅助说明、状态信息和图表标注使用 `12px`。
- 用户可见的文字字号不得小于 `12px`，不得通过响应式断点、组件覆盖或第三方组件样式将文字压缩到 `12px` 以下。
- 移动端可以将导航和次级内容调整为 `14px` 以适应窄屏，但页面标题、面板标题和核心数值仍应保持 `16px`；最小字号仍为 `12px`。
- ECharts 的坐标轴名称、坐标轴刻度和图例等文字字号不得小于 `12px`，并应随容器尺寸变化保持可读性。
- 新增字号应优先复用现有 SCSS/CSS 设计变量或统一样式规则；确需使用其他字号时，应说明设计原因并确保不破坏最小字号约束。

### Dashboard 响应式布局

- Dashboard 必须使用可伸缩布局占满浏览器可用宽度和高度，不得使用 `min-width: 1100px`、`max-width: 1920px` 等会造成横向溢出或超宽屏留白的固定页面约束。
- 桌面大屏（`>= 1280px`）使用左侧配置栏、中间核心内容区、右侧状态与预测栏三栏布局；三栏应使用 `minmax()`、比例列宽或等效的自适应方式填充可用宽度。
- 平板（`768px–1279px`）使用左侧配置栏与中间内容区两列布局，右侧内容独立排列；右侧内部模块应根据可用空间自适应，不得挤压或撑破页面。
- 手机或浏览器放大后的窄屏（`< 768px`）使用单列纵向布局，所有业务模块必须保留并可通过纵向滚动访问。
- 页面根节点和主要布局容器应设置 `min-width: 0`、`max-width: 100%` 等收缩约束，避免 Grid/Flex 子元素撑开父容器；页面不得出现横向滚动条。
- Dashboard 的内容区域应至少填满扣除顶部导航后的可视高度。三列在桌面布局下应保持相近的整体高度，不能只拉伸单个底部模块。
- 中间的“刀具当前位置 · 实时数字孪生”区域是核心弹性区域，应优先吸收中间栏剩余高度并随视口高度变化；下方工艺参数图表保持内容高度，不得通过单独拉长该模块制造空白。
- 图表容器必须使用容器宽高进行自适应，并支持 ECharts `autoresize` 或等效的重绘机制；禁止固定宽度导致裁切、空白或缩放后尺寸坍缩。
- 响应式布局修改不得隐藏业务数据、监控图表或交互模块；只允许调整排列、尺寸、间距和文字省略方式。

Dashboard 响应式改动至少应检查以下视口和浏览器缩放比例：

- 视口：`2560×1440`、`1920×1080`、`1440×900`、`1024×768`、`768×1024`、`390×844`。
- 缩放：`80%`、`100%`、`125%`、`150%`。
- 验收：`document.documentElement.scrollWidth` 不大于视口宽度；超宽屏无两侧固定留白；窄屏所有模块可纵向访问；图表无裁切和异常空白。

## 8. 当前不纳入的约束

以下内容暂不作为本项目的强制规范：

- ESLint、Prettier 或 Vitest 的配置与执行要求。
- Git 提交信息格式和分支命名格式。
- UTF-8、乱码检查或专门的编码验收流程。
- 对现有目录结构的立即迁移。

如果后续引入上述工具或规则，应同步更新本文件，并明确生效范围和验证命令。
